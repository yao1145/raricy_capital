# 未认领款人工核对（已实现）

两个处理入口：**原路全额退款** 与 **严格关联已有申购单**。控制台面板与后端接口按
同一份共享契约实现；操作步骤见 [UNCLAIMED_REVIEW.md](../usage/UNCLAIMED_REVIEW.md)。

本功能覆盖账务、收付款队列、服务接口与控制台。策略参数与基金经济规则保持冻结。
设计说明与操作手册分开维护；真实账户和服务器验收仍待部署环境完成。

## 1. 处理原则

未认领款是「真实到账但无法自动匹配」的钱：它已经计为负债，不属于基金资产，也不产生份额。

- **可以修**：付款人、金额、基金都对，只是**附言填错或漏填**导致自动匹配失败 —— 人工关联到
  那一张已有申购单，保留原始附言，并写明关联理由。
- **不能修**：金额不符、重复付款、订单已取消/已发行/已退款、到账时间在订单有效期之外、
  找不到对应订单 —— 核实后原路全额退款，由用户重新申购。
- **不猜**：流水缺失、来源或时间无法确认、存在多笔歧义 —— 继续隔离（待核对），等待更多证据。
  没有「强制清零」按钮，系统也不会替管理人新建、补写或倒签申购单。

## 2. 接口

### HTTP（运营台）

| 方法 | 路径 | 请求 | 响应 |
| --- | --- | --- | --- |
| `GET` | `/api/unclaimed?fund_id=&status=` | — | `{unclaimed:[…], count, total_units}`（按筛选合计） |
| `GET` | `/api/funds/{fund_id}/unclaimed/{unclaimed_id}` | — | `{record: 明细}` |
| `POST` | `/api/funds/{fund_id}/unclaimed/{unclaimed_id}/preview` | `{action:'link'\|'refund', subscription_id?}` | `{preview:{eligible, errors[], action, record, subscription}, live}` |
| `POST` | `/api/funds/{fund_id}/unclaimed/{unclaimed_id}/resolve` | `{action, subscription_id?, version, reason}` | `{record}` |

- 明细包含到账要素（流水 ID、上游流水号、交易记录行、付款人、整数金额、权威到账时间、
  原始附言、记录版本）、候选申购单、核对历史与显示状态。
- **入参一律不接受**金额、付款人、到账时间、`verified_transfer` 或操作人身份；`actor` 由服务端
  从已认证会话/控制令牌派生为不透明摘要，页面与请求体都不携带。
- 预览与提交都会**重新读取上游权威到账记录**；提交在同一个事务里做版本原子校验（CAS）。
- `live=false` 时：`GET` 与预览照常（无账务副作用），`resolve` 在读取站点之前即以
  `live_required` 拒绝，**不生成任何以后会自动付款的队列，也不改动已冻结/已结算的账**。

### 领域方法

```python
FundLedger.unclaimed(fund_id=None, status=None) -> list[dict]
FundLedger.unclaimed_detail(fund_id, unclaimed_id, now_ms) -> dict
FundLedger.preview_unclaimed(fund_id, unclaimed_id, action, *, subscription_id=None,
                             verified_transfer=None, now_ms) -> dict   # 只读
FundLedger.resolve_unclaimed(fund_id, unclaimed_id, action, *, version, reason, actor,
                             verified_transfer, now_ms, subscription_id=None) -> dict
FundService.unclaimed / unclaimed_detail / preview_unclaimed / resolve_unclaimed
```

`reason` 必填且不超过 500 字，`actor` 不超过 128 字且不透明；`live` 只在服务/Web 层把关，
领域层没有 `live` 参数。预览不写快照、不补历史、不做任何写入。

## 3. 状态、版本与并发

| 存储状态 | 显示 |
| --- | --- |
| `unclaimed` | 待核对 |
| `linked` | 已关联申购单 |
| `refund_queued` | 退款已排队 · **尚未付款**（有等待原因时显示，如现金不足） |
| 由付款进度派生 | `refund_unknown` → 退款结果待确认（未知，需先对账）；`refunded` → 已退款 |

一笔流水只允许一个处理结果：`version` 默认 0，成功处理后自增。**没有持久化的「核对中」编辑锁**：
「正在核对」只是操作员本机的临时界面状态；提交阶段用「乐观预览 + 原子 CAS」代替锁——版本变化时
服务端拒绝提交，面板提示重新加载并重新核对。刷新页面、换人接手都不会留下悬挂的锁。

## 4. 账务口径（净值中性）

- 关联：未认领款 −A，待确认本金与预收费用合计 +A；份额与资本流入仍由**既有月末流程**发行，
  不追溯分红、不回填已结算月份。
- 退款：未认领款 −A，应付款 +A，净资产不变；实际付款后钱包与应付款同步减少。
  只退回原付款人、只按原始金额，付款业务键由「基金 + 上游流水 ID」派生且长度受限，
  重试复用同一个键与同一条付款意图。
- 退款进入独立处理的持久付款队列：**排队不等于已付款**；现金不足时保持排队并记录等待原因，发送前读取最新站点余额，按账簿与实际余额的较低值扣除待确认申购、预收费用、
  其他未认领款与其他应付款；余额不足或不可读取时等待。退款确认采用最新绝对余额，避免已反映的扣款再扣一次。
  请求超时或结果未知时先对账（先查权威出账流水），只有完整扫描中唯一匹配、付款人与金额可核实，且最新余额读取成功时才结案。
  完整扫描确认没有匹配出账后，才允许复用同一业务键重试；扫描失败、不完整或歧义时保持结果未知。
- 回查使用**独立、有界的客户端流水游标**，不改动收款轮询游标，也不影响正常付款轮询。

## 5. 控制台实现要点（`static/`）

- 面板：基金/状态筛选、未处理笔数与合计、逐笔列表、详情、候选申购单与原因、核对历史、
  处理方式与必填理由、候选项选择、预览校验、最终确认摘要、按版本提交。
- 所有上游文本一律经 `textContent` 写入 DOM（不使用 `innerHTML`）；候选人、理由、历史中的
  站点返回值按纯文本显示。
- 5 秒轮询只更新真正变化的行/字段：列表按内容签名判断是否需要重建，**填写中的理由、候选项与
  预览不会被覆盖**（有草稿时详情自动刷新暂停并给出提示），控件焦点与滚动位置保留。
- 每次登录/登出递增 `sessionEpoch`，晚到的旧请求不得回填界面；退出登录时清空列表、详情、
  草稿与预览（面板内不保留任何流水信息）。
- `live=false` 时预览照常、**提交按钮禁用并说明原因**；界面只显示真实状态，排队/未知/已付款
  三者分开显示，不把付款意图写成已退款。
