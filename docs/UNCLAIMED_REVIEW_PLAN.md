# 未认领款人工核对方案

**待审阅方案，尚未实现。** 推荐同时提供「原路退款」与「严格关联申购单」两个处理入口。

## 1. 当前问题

现有 `ledger.receive_transfer` 已保存未匹配的到账，并将金额从基金净资产中扣除；界面只显示总额，没有逐笔核对入口。未认领记录尚未保存对应的上游 `transfer_id`，需补齐关联。现有付款队列、通知队列和管理端鉴权可以复用。

## 2. 管理人操作流程

**未认领款列表 → 查看详情及候选订单 → 回查站点到账记录 → 选择处理 → 确认摘要并填写理由 → 跟踪结果。**

列表按基金、状态、日期筛选，展示未处理数量及总额。详情展示流水 ID、付款人 ID、金额、权威到账时间、附言、候选申购单、核对历史；账户口令与管理令牌不出现在页面和记录中。

| 处理方式 | 允许条件 | 处理结果 |
| --- | --- | --- |
| 原路全额退款 | 确认真实入账、付款人明确且该笔尚未处理 | 生成付款队列，只退给原付款人，金额不能编辑 |
| 关联已有申购单 | 同基金、同付款人、实付金额完全一致；到账在订单创建后、180 秒有效期内；订单尚未付款、未取消、未发行或退款 | 转为待确认申购，按既有规则月末确认份额 |
| 保留待核对 | 流水缺失、来源或时间不能确认、重复记录存在歧义 | 继续隔离，不转账、不发份额 |

人工关联可以纠正「附言填错」导致的漏匹配，但保留原始附言，必须记录关联理由。不能修改到账时间、金额、手续费、付款人，也不能由管理人代建或倒签申购单。金额错误、重复付款、超过有效期、无有效订单，核实后全额退款，由用户重新申购。

关联时继续沿用现有申购窗口和顺延规则；**已经结算的月份不补登记、不追溯分红**。到期前已真实到账、但后来才发现的付款不能仅因发现晚而判断超时；必须使用站点的权威时间。若处理需要改写已冻结或已结算的快照，第一版保持待核对或退款，不自动改历史账。

## 3. 账务口径

人工核对本身不影响净值、份额、资本流入或已实现利润。金额始终用整数 1e-4 单位，份额用整数 1e-8 单位。

- **退款登记**：未认领款减少 A，应付款增加 A，净资产不变；实际付款后钱包与应付款同步减少。现金不足显示「等待可用现金」，不挪用其他申购款。
- **关联订单**：未认领款减少 A，待确认本金与预收费用合计增加 A，净资产不变；只有既有月末流程才发行份额和确认资本流入。
- 一笔流水只能选择一次处理结果。退款排队与退款成功分开显示，不能把已生成付款意图当成已退款。

## 4. 状态、幂等与审计

显示状态：待核对、核对中、已关联、退款排队、退款待确认、已退款。核对中允许释放或超时恢复待核对，不永久锁住；释放也写审计记录。

回查站点在数据库事务外完成；提交时重新校验记录版本、订单状态与基金截止快照，所有本地账务和处理结果在一个事务内提交。两个人同时处理或重复点击，只允许一项结果，版本冲突提示重新加载。

退款业务键根据基金和流水生成固定摘要，符合站点长度限制；重试复用同一个付款记录和幂等键。请求超时或结果未知时先查账，不能创建另一笔退款。通知通过现有 outbox 在提交后发送，通知重试不会重复记账。

保存原始到账信息及操作理由、管理会话审计 ID、处理前后状态、时间、关联订单/付款 ID。当前是共享管理令牌，审计能追踪管理会话，**不声称能验证具体个人身份**；可选操作人备注仅供管理人辨识。普通日志只记稳定错误码和业务 ID。

## 5. 实现范围

- `ledger.py`：逐笔列表/详情、原路退款与关联订单的原子处理。
- `runtime.py/client.py`：回查指定基金的权威流水，独立读取，不改变收款轮询游标。
- `web.py`：列表、详情、处理预览与确认接口，沿用令牌、同源和 JSON 守卫。
- 控制台：新增「未认领款」面板，二次确认展示付款人、金额、处理方式与必填理由；操作后显示付款进度。
- `live=false` 只展示验证和处理预览，**不写正式处理状态、不生成以后会自动付款的队列**。

历史数据仅在同基金、付款人、金额、时间和附言唯一对应上游流水时补齐关联；不能唯一确定则继续隔离，等待更多证据，不提供强制清零按钮。

## 6. 方案选择与验收

推荐上述两入口方案：能保留有效申购，也能安全退回错误付款。更小的首版可只提供原路退款，代价是漏匹配的有效订单也需重新申购。

针对性验收包括：重复退款只付一次；退款超时先对账；不匹配或超时订单不能关联；核对前后净值中性；并发处理冲突不改账；历史缺关联保持隔离；只读模式无账务副作用。
